# Browser DID binding research

Research class: storage-ffi
Research status: ready
Decision date: 2026-09-09
Source retrieval date: 2026-09-09
Research blockers: none

## Problem and existing implementation

The SDK currently has no supported browser FFI. Its target gate proves only
that selected Rust crates compile to `wasm32-unknown-unknown`.
`identus-did` already owns W3C DID Core parsing, exact round trips, component
views, 2,048-byte DID and 4,096-byte DID URL limits, and stable redacted errors.
The browser adapter should reuse that implementation rather than copy grammar
or add JavaScript dependencies to the domain crate.

## Compatibility and dependency evidence

The runtime leaf adds exact `wasm-bindgen = 0.2.121` with its default `std`
feature; the dev-only test harness is exact 0.3.71. Both declare MSRV Rust 1.77
and MIT OR Apache-2.0, below and compatible with the SDK's exact Rust 1.98.1
etalon. Those upstream tags plus the immutable SDK base provide license and
provenance evidence. wasm-pack 0.15.0 and wasm-bindgen-cli 0.2.121 come from the
repository-pinned Nix input and remain slow-line tooling. The root lock and `cargo tree` record the direct
and resolved dependency cone; no dependency-owned type crosses the generated
TypeScript contract. Root `cargo deny`, pinned-advisory `cargo audit`, exact
locks and tag SHAs provide supply-chain evidence.

The measured normal/build tree contains 35 unique rendered lines including the
SDK/DID graph; enabling dev edges contains 56. Direct dependencies are
`identus-did` and wasm-bindgen, with wasm-bindgen-test dev-only.

The package target is `web`: native browser ESM with an explicit asynchronous
default initializer and no mandatory Node/npm/bundler runtime. TypeScript
declarations are generated by default. A consumer may import the same ESM from
React after application bootstrap awaits initialization; no React code belongs
in the SDK package.

Public and wire compatibility is additive and experimental: no existing Rust
or wire representation changes, and browser API version 1 is a new facade.
DID Core 1.0 is final; wasm-bindgen is an implementation tool rather than an
identity protocol or draft. Browser and tool target evidence is limited to the
commands below.

## Security, privacy and maintenance evidence

The adapter accepts only public identifier strings and delegates all grammar
and byte bounds before constructing exported values. Failures throw an
SDK-owned object with one of two constant codes; caller text and parser details
are excluded. No secret, key, storage, network or ambient browser authority is
present.

Exported records and errors are WASM-owned classes. JavaScript callers must
call `free()` when retaining many instances; automatic finalization is a
best-effort convenience, not the lifecycle contract. The functions are
synchronous and single-threaded. No `SharedArrayBuffer`, worker, thread or
blocking-main-thread behavior is enabled. The generated module requires
loading JavaScript plus a `.wasm` resource and an awaited initializer; strict
CSP therefore needs `wasm-unsafe-eval` where the browser requires it or an
allowed WebAssembly compilation policy, plus same-origin/CORS delivery for the
WASM resource. Applications own CSP, caching and asset URLs. Cache invalidation
must key both files by the same content/release revision.

The package is unpublished and experimental. Chromium and Firefox runtime
tests are weekly/manual evidence, not a browser-version support matrix. Size is
measured for the uncompressed release JS, TypeScript and WASM outputs without
inventing a budget. ABI/API version `1` and a committed declaration snapshot
make breaking drift reviewable.

Two release package trees were byte-identical. Uncompressed measurements were
14,896-byte JavaScript, 4,360-byte public TypeScript declarations, 33,833-byte
WASM, 1,594-byte WASM declarations and a 319-byte package manifest. Local Chrome
152.0.7977.83 with ChromeDriver 152.0.7977.65 passed both browser test families;
the slow Ubuntu gate owns the independent Firefox receipt.

Authored Rust remains `unsafe_code = "forbid"`; wasm-bindgen and browser
runtimes contain dependency-owned unsafe and native code whose boundary is
limited by exact pins and executable browser evidence. This is the maintenance,
release and security posture until a separate activation decision.

## Rejected or deferred candidates

Direct `web-sys`/`js-sys`, `serde-wasm-bindgen`, UniFFI browser generation and
a bundler-specific dependency are rejected or deferred in the candidate table.
Node, React Native, DOM/network APIs, async calls, workers, threads, secrets and
publication are unrun because they are outside this value-only slice.

## Open questions and blockers

There are no implementation blockers. A future named React consumer may need a
separate bundler fixture; this direct `web` ESM proof deliberately does not
select that consumer's JavaScript build system.

## Evidence commands

Focused exact commands run locked host tests, `cargo build -p identus-wasm-did
--target wasm32-unknown-unknown`, two `wasm-pack build --target web --release`
runs, full-tree and TypeScript snapshot comparison, size/hash reporting, and
headless Chrome/Firefox `wasm-pack test` runs. Root audit/deny, factory, Cargo
and Nix gates still apply. The fast PR line remains unchanged; browser
execution belongs to the scheduled/manual slow Ubuntu job.

Unrun checks are Node, React Native, downstream React bundlers, physical device,
publication, release, signing, certification and browser-version matrices.

Rollback removes the leaf crate, WASM devshell, slow job, snapshots and
inventory entry. It does not change `identus-did`, persisted values, support
policy or downstream repositories.
