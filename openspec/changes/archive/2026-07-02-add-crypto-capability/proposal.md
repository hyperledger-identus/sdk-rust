## Why

The Identus platform's cryptographic capability currently lives in two places: the **canonical KMP `apollo`** (full surface — Ed25519/X25519/secp256k1 key generation + signing + verification, derivation, secure random, ed→x25519 conversion, curve validation) and **neoprism's `lib/apollo`** (a partial Rust port — verify-only for Ed25519/X25519, sign+verify for secp256k1, plus hashing/JWK/encodings, consumed by neoprism's `did-prism` resolver). The `sdk-rust` workspace has a `crates/crypto` stub but no capability. The Identus SDK needs a **single canonical crypto capability** that the TypeScript, Swift, and KMP bindings are ported *from* — and Rust is the reference implementation language. This change introduces `identus-crypto` as that canonical home: the neoprism Rust port, completed to full sign/verify/generate across all curves, rehomed into the SDK, and re-platformed onto the workspace's redaction-safe `IdentusError` contract. It is the first real content in the `crypto` domain-primitive crate and the first adopter of the `core-error-conventions` two-surface error-bridging pattern.

**Hexagonal scope.** `identus-crypto` owns **primitive crypto operations on key material** (bytes-in, bytes-out) — neoprism-`apollo`-style concrete curve types plus encoding/verification trait polymorphism. The only infrastructure **port** is `SecureRandom` (entropy), the one place a **known** second backend exists (`ring` breaks on `wasm32`; a `getrandom` wasm adapter is needed by the future TS binding) — so `SecureRandom` is a port defined in `identus-crypto`, but its **adapters live in the outer-boundary `identus-adapters-entropy` crate** (created by the consumed `add-adapter-crate-layer` change), not in the domain: the `ring`-backed native adapter is filled here into that crate, and the `getrandom`/wasm adapter + `wasm` feature are deferred to the future TS/wasm binding change (also landing in `identus-adapters-entropy`). Key generation and mnemonic creation take an **injected** `&mut impl SecureRandom` (dependency injection) rather than a zero-arg default, since the domain cannot reach an outer-boundary adapter. Curve operations, hashing, derivation, and conversion stay concrete: `ed25519-dalek`/`k256`/`p256`/`x25519-dalek`/`sha2`/`hmac`/`pbkdf2` have no known second backend, so a `Signer`/`Verifier`/`KeyGenerator` port would be a single-adapter port with no known second impl to write. Hashing uses pure `sha2` (wasm-safe), so no `Digest` port is needed. Because `ring` lives in the outer-boundary adapter crate (not in `identus-crypto`), `identus-crypto` builds on `wasm32-unknown-unknown` with **default features** — the wasm limitation is confined to `identus-adapters-entropy`. **Key management is out of scope**: `KeyHandle`, `KeyStore`, `SecretResolver`, non-exportable signing, and hardware/`KMS`-bound signers are an `identus-wallet` concern per the secure-storage boundary, not a primitive-crypto one; they land in a separate change. This reconciles the seed's `crypto` doc-comment, which over-claimed "hardware/KMS adapter traits" — that remit belongs to `identus-wallet`/`identus-adapters`.

## What Changes

- Implement `identus-crypto` (currently a `COMPONENT`-only stub) as the canonical crypto capability, owning the Rust source (ported in from neoprism's `lib/apollo`; neoprism is **not** a dependency — its crate is the *source of the port*, not a consumed crate).
- Complete the sign/generate side that neoprism's port omits: Ed25519 and X25519 gain `PrivateKey` + `KeyPair` + `generate` + `sign` (+ DH for X25519), matching the KMP `apollo` surface; secp256k1 keeps its existing full sign/verify including the **JVM-compat verification** (normalize-s + bitcoin-transcode) preserved verbatim.
- Add P-256 (secp256r1) for parity with KMP `apollo`'s `KMMEllipticCurve` (a gap in neoprism's Rust port).
- Add the encoding/JWK/hash primitives: `EncodeVec`, `EncodeArray<const N>`, `Verifiable` traits; `Jwk` + `EncodeJwk`; `Sha256Digest` (+ `Sha512Digest` for derivation, both pure-`sha2` — wasm-safe, no `ring`); `Base64UrlStrNoPad`; `HexStr`. These traits are interface polymorphism over the crypto types, not infrastructure ports.
- Add the extended capability surface: `SecureRandom` (the **single infrastructure port** — entropy; the trait is defined in `identus-crypto`, and its `ring`-backed adapter is implemented in the outer-boundary `identus-adapters-entropy` crate created by the consumed `add-adapter-crate-layer` change; the `getrandom`-backed wasm adapter + `wasm` feature are deferred to the future TS/wasm binding change, also in `identus-adapters-entropy`). Key generation and mnemonic creation take an injected `&mut impl SecureRandom` (dependency injection), BIP32 `HDKey` (secp256k1 hierarchical derivation), SLIP-0010 `EdHDKey` (ed25519 hierarchical derivation from seed), BIP39 `MnemonicHelper` (+ English wordlist, PBKDF2-SHA512 seed derivation), and `ConvertEd25519` (ed25519 → x25519 private key conversion).
- Adopt the two-surface error model: a rich, idiomatic `crypto::Error` (carrying runtime detail like `InvalidKeySize { expected, actual, key_type }` for logs) plus `to_identus_error()` mapping to the redaction-safe `IdentusError` with a stable `ErrorCode` catalog and `CapabilityId("crypto")`. `crypto` is the first crate to ship the bridging convention documented in `core-error-conventions`.
- Feature-gate the algorithms (matching neoprism's gating style), with **default = all features enabled** so the canonical build and every binding's default path compile the full surface.

## Capabilities

### New Capabilities

- `crypto`: the canonical cryptographic capability — key types, signatures, key generation, JWK, hashing, derivation (BIP32/SLIP-0010/BIP39), secure random, and ed→x25519 conversion — with the two-surface error-bridging convention, feature-gated with all-on default. Scope: primitive operations on key *material* (neoprism-`apollo`-style); `SecureRandom` is the single infrastructure **port** (defined here; its `ring` adapter lives in the consumed `identus-adapters-entropy` outer-boundary crate, injected into `generate`/`create_random_mnemonics`); key management (`KeyHandle`/`KeyStore`/non-exportable/HSM signing) is out of scope, deferred to `identus-wallet`.

This change consumes (but does not modify) `crate-ring-layout` (`identus-crypto` stays in the domain-primitives layer, depending only on `identus-core`) and consumes `add-adapter-crate-layer` (which relaxes the ring-layout's fixed crate count to allow `identus-adapters-<family>` crates and creates the `identus-adapters-entropy` skeleton that this change fills with the `ring` adapter). It also consumes `workspace-dependency-conventions` (all external crates declared at workspace level, referenced via `.workspace = true`) and `nix-tooling` (external deps fall under the existing `rust-audit` / `cargo-deny` checks). No spec deltas are produced for those capabilities.

## Impact

- **`crates/crypto/Cargo.toml`**: gains external dependencies (declared via `.workspace = true` per `workspace-dependency-conventions`) — `ed25519-dalek`, `k256` (+`arithmetic`,`ecdsa`), `p256` (+same), `x25519-dalek`, `sha2` (hashing + derivation), `hmac`, `pbkdf2`, `base64`, `hex` (**no `ring`** — the `ring`-backed entropy adapter lives in `identus-adapters-entropy`, not in the domain); plus a feature map with `default = all` (`ed25519`,`x25519`,`secp256k1`,`secp256r1`,`hash`,`hex`,`base64`,`jwk`,`derivation` — no `securerandom` feature, since the `SecureRandom` port trait is zero-dependency and always available; no `wasm` feature in this change). Root `Cargo.toml` `[workspace.dependencies]` gains the corresponding entries (the `ring` entry is added by `add-adapter-crate-layer`, not here).
- **`crates/crypto/src/`**: new modules — `error.rs`, `enc.rs`, `jwk.rs`, `hash.rs`, `base64.rs`, `hex.rs`, `convert.rs`, `securerandom.rs` (the `SecureRandom` **port trait only** — no `ring` impl), `crypto/{ed25519,x25519,secp256k1,secp256r1}.rs` (each `*KeyPair::generate` takes an injected `&mut impl SecureRandom`), `derivation/{hdkey,edhdkey,mnemonic}.rs` (+ wordlist; `MnemonicHelper::create_random_mnemonics` takes an injected `&mut impl SecureRandom`). `lib.rs` keeps `COMPONENT`.
- **`crates/adapters-entropy/src/`**: the `ring`-backed `SecureRandom` adapter is implemented here (behind the `ring` feature created by `add-adapter-crate-layer`), implementing `identus_crypto::SecureRandom` via `ring::rand::SystemRandom`. A deterministic test adapter may land behind a `deterministic` feature for cross-crate consumers.
- **Tests**: Ed25519/X25519/secp256k1/P-256 unit tests (each `generate`/`create_random_mnemonics` call injects a small in-test deterministic `SecureRandom` impl — `identus-crypto` cannot dev-depend on the outer-boundary adapter crate), the 50-vector JVM-compat secp256k1 suite (ported from neoprism), JWK roundtrips, BIP32/SLIP-0010/BIP39 known vectors, ed→x25519 conversion vectors, a wasm-clean assertion (`cargo build -p identus-crypto --target wasm32-unknown-unknown` with default features succeeds), and error-bridging tests asserting every `crypto::Error` variant maps to a stable `IdentusError` code whose `Display` carries no runtime detail.
- **Assumes prior changes landed**: `add-workspace-dependency-conventions` (external deps declared at workspace level) and `add-adapter-crate-layer` (creates the `identus-adapters-entropy` skeleton and relaxes the ring-layout to admit adapter-family crates). The crypto crate's external deps enter a single-source, workspace-level graph; the `ring`-backed entropy adapter is filled into the crate created by `add-adapter-crate-layer`.
- **No change to neoprism**: this change ports *in*; migrating neoprism to depend on `identus-crypto` (replacing its own `lib/apollo`) is a separate future workspace change, explicitly out of scope here.
- **`ring` ↔ WASM tradeoff (scoped to `identus-adapters-entropy`, not `identus-crypto`)**: `ring` does not build on `wasm32-unknown-unknown`, so it lives in the outer-boundary `identus-adapters-entropy` crate (behind a `ring` feature, `default = []`), **not** in `identus-crypto`. Consequence: `identus-crypto` builds on `wasm32` with **default features** (it has no `ring` dependency; only the port trait is defined here); the wasm limitation is confined to the adapter crate. The `getrandom`-backed wasm adapter + `wasm` feature land in `identus-adapters-entropy` in the future TS/wasm binding change. The devshell already provides the `wasm32-unknown-unknown` target for the future change.
