# ADR 0088: use caller spans for first-party procedural-macro output

- **Status:** Accepted
- **Date:** 2026-09-08
- **Decision authority:** sdk-rust issue #189
- **Constraint impact:** strengthens `SDK-SEC-001` for direct first-party
  procedural-macro output and narrows `SDK-LIM-008`

## Context

ADR 0087 makes `unsafe_code = "forbid"` effective for authored first-party
targets. Rust 1.98.1 intentionally skips the lint for expansion spans where
`span.allows_unsafe()` is true, so a safe procedural macro can otherwise emit
unsafe syntax into an opted-in consumer without a diagnostic.

`identus-derive` is the only first-party procedural-macro crate. Its
`#[identus::port]` attribute returns parsed caller input unchanged. Its
`#[derive(Newtype)]` implementation has finite, direct `quote` templates for
string, byte and numeric newtypes. Those templates contain no unsafe syntax,
but their default generated spans do not make the workspace forbid a
preventive control against future unsafe output.

Stable Rust 1.98.1 probes established that generated unsafe syntax is rejected
when its direct tokens carry a span from the caller input. The same syntax
compiled when emitted with parsed/default, `Span::call_site()` or
`Span::mixed_site()` spans. Re-spanning only the `unsafe` identifier was not
sufficient; the generated syntax context must carry the caller span.

## Decision

1. Every direct `Newtype` expansion template uses `quote_spanned!` with the
   input type identifier span. Interpolated caller tokens retain their own
   spans as defined by `quote`.
2. The unchanged `port` attribute remains a token-preserving pass-through;
   errors continue to use the annotated identifier span.
3. A dependency-free stable compile-fail fixture proves that caller-spanned
   procedural-macro output containing unsafe syntax is rejected specifically
   by the inherited unsafe-code forbid.
4. Existing runtime and trybuild suites remain the semantic and diagnostic
   regression evidence for every supported `Newtype` shape.
5. No expanded-source snapshot, lexical claim, new scanner, nightly lane or
   `RUSTC_BOOTSTRAP` escape is introduced.

## Assurance boundary

This decision covers direct syntax generated by first-party expansion
templates that consistently use caller-origin spans. It does not certify
external procedural macros, dependency internals, nested macro expansions,
arbitrary token transformations, logical safety or side-channel behavior.
Those residual cases remain disclosed by `SDK-LIM-008` and dependency review.

## Consequences

- Rust itself becomes the preventive unsafe-code gate for direct first-party
  `Newtype` output without adding a dependency or CI lane.
- Diagnostics for generated syntax point at the derived type, which is an
  appropriate consumer-visible origin for generated implementation failures.
- Template authors must preserve caller-spanned generation. The committed
  behavioral probe protects the compiler premise, while review and existing
  finite-shape tests protect macro-template maintenance.
- The rule is deliberately narrower than a claim that all expanded output is
  linted.

## Rollback

Revert the issue #189 change, restore default `quote!` templates and broaden
`SDK-LIM-008` to all procedural-macro output. No public API, wire format,
dependency, runtime data or downstream migration is involved.
