## MODIFIED Requirements

### Requirement: The assurance claim remains first-party and evidence-bounded

The unsafe-code prohibition SHALL apply to authored first-party SDK source and
direct Rust item syntax generated by a first-party procedural macro. Completed
direct `identus-derive` output SHALL be parsed and recursively rejected before
emission if it contains an unsafe block, unsafe signature, unsafe trait, unsafe
trait implementation, unsafe extern block, `global_asm!`,
`allow_internal_unsafe`, or a Rust unsafe attribute (`export_name`,
`link_section`, `naked`, or `no_mangle`). Focused machine tests SHALL cover
every rejected category, nested syntax, unsafe attributes latent in nested
`cfg_attr` branches and safe output; existing finite-shape runtime and trybuild
suites SHALL remain compatible.

The prohibition SHALL NOT be represented as linting external dependency
internals, executing or uniformly rejecting nested procedural-macro output,
certifying external procedural macros, proving logical or side-channel safety,
or exercising unsupported feature/target combinations. Dependency unsafe or
native code SHALL continue to be evaluated in dependency research and
integration ADRs. External, nested or otherwise uninspected expansion output
SHALL remain an explicit indexed limitation.

#### Scenario: First-party direct output contains unsafe syntax

- **WHEN** completed direct `identus-derive` output contains any enumerated
  unsafe construct or attribute, including inside a nested item or expression
- **THEN** the macro returns a compile error instead of emitting that output

#### Scenario: Safe first-party output remains compatible

- **WHEN** supported string, byte and numeric `Newtype` shapes are expanded
- **THEN** existing runtime and trybuild suites pass with unchanged generated
  spans and no public API, wire, runtime, package, target or MSRV change

#### Scenario: External or nested macro later emits unsafe syntax

- **WHEN** external procedural-macro output or a nested macro expansion carries
  a span for which rustc intentionally allows internal unsafe
- **THEN** the SDK does not claim the direct-output guard catches it and retains
  `SDK-LIM-008` plus dependency/macro review for that residual boundary

#### Scenario: Adopted dependency contains reviewed unsafe code

- **WHEN** Cargo compiles an external dependency under dependency cap-lints
- **THEN** the first-party gate does not claim to reject that source, and its
  unsafe/native posture remains explicit dependency-decision evidence
