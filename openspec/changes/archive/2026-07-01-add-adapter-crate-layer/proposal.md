## Why

The `crate-ring-layout` currently fixes the workspace at a single `identus-adapters` crate in the `outer-boundary` layer, intended to accumulate every concrete adapter (transport, storage, resolver, key-management/HSM, and now entropy) behind cargo features. As the adapter set grows this has two structural costs: (1) **compile-time leakage** — cargo unifies features across the graph, so any production crate that depends on `identus-adapters` to reach one adapter transitively compiles every other enabled adapter's dependency tree (`rusqlite`, HSM SDKs, HTTP clients, …); and (2) **cohesion loss** — a single "adapters" crate has no single responsibility and becomes a grab-bag where "just put it in adapters" is the path of least resistance. The hexagonal remedy is to make `outer-boundary` a *layer* of small, cohesive adapter crates — one per **port family** — so each adapter's dependency graph is isolated and each crate has one review surface. This change relaxes the ring-layout's fixed crate count to allow additional `identus-adapters-<family>` crates in `outer-boundary`, establishes the conventions that keep them from rotting, and creates the first such crate, `identus-adapters-entropy`, as the home for the `SecureRandom` adapter that `add-crypto-capability` will fill (the `ring`-backed native adapter now; the `getrandom`-backed wasm adapter in a future TS/wasm binding change).

## What Changes

- Relax the `crate-ring-layout` fixed-crate-count stance: the workspace SHALL contain the enumerated baseline crates *plus* any number of `identus-adapters-<family>` crates in the `outer-boundary` layer; the conformance guard SHALL derive the member count and the outer/verification crate set from `LAYER_RULES` rather than hard-coded literals or a hand-maintained `OUTER_CRATES` list, so additional adapter-family crates are admitted by adding them to `LAYER_RULES` + root `[workspace.dependencies]` without further spec/guard edits.
- Make the spec's own crate-count statements non-literal and tolerant of future adapter-family crates: RENAME `### Requirement: Twelve crate stubs at minimal code depth` → `### Requirement: Crate stubs at minimal code depth` and rewrite its body to enumerate the founding runtime stubs plus `identus-adapters-entropy`, admitting further `identus-adapters-<family>` stubs by reference to the adapter-family convention without a fixed total count; and MODIFY `### Requirement: Workspace dependency map` to state that `[workspace.dependencies]` maps every `LAYER_RULES` member (count derived from `LAYER_RULES`, no literal `13`/`14`/`15`).
- Add an adapter-family convention: `outer-boundary` adapter crates follow `identus-adapters-<family>` naming, each owns the concrete adapters for a single port family (entropy, storage, transport, resolver, openid4vc), expose `default = []` (adapters are opt-in), and SHALL NOT cross-couple (no adapter-family crate depends on another adapter-family crate). The existing `identus-adapters` crate is retained as the cross-cutting/facade home for adapter concerns that don't belong to a single port family.
- Create `identus-adapters-entropy` as the first adapter-family crate: a minimal stub (`COMPONENT` + `Cargo.toml` depending on `identus-crypto` + `identus-core`, `ring` optional behind a `ring` feature, `default = []`), member of `outer-boundary`, registered in root `[workspace.dependencies]` and `LAYER_RULES`. Add `ring` to root `[workspace.dependencies]` (entropy is the sole workspace consumer of `ring`). The adapter *content* (the `ring`-backed `SecureRandom` impl) is filled by `add-crypto-capability`, which consumes this change.
- Restate the dependency-direction rule for adapter-family crates: no production crate (foundation through orchestration) SHALL depend on any `identus-adapters-<family>` crate (already implied by the inward policy); adapter-family crates are consumed only by binaries, examples, and `identus-bindings` (the composition root).

## Capabilities

### Modified Capabilities

- `crate-ring-layout`: relaxed, extensible crate count; adapter-family layer conventions; `identus-adapters-entropy` membership; guard derives counts/outer-set from `LAYER_RULES`.

This change is consumed by `add-crypto-capability` (which fills `identus-adapters-entropy` with the `ring` adapter and defines the `SecureRandom` port in `identus-crypto`). It **intentionally collides** with `add-domain-newtype-macro` on two shared requirement headers — `Crate stubs at minimal code depth` (this change renames it from `Twelve crate stubs at minimal code depth` and rewrites the body; `add-domain-newtype-macro` adds the `identus-derive` exclusion to the same requirement) and `Workspace dependency map` (both rewrite the count to a `LAYER_RULES`-derived form). The collision is resolved by archive ordering: **`add-adapter-crate-layer` archives first** (its RENAMED + MODIFIED blocks are self-contained and do not carry `add-domain-newtype-macro`'s `identus-derive` content), then `add-domain-newtype-macro` archives second and its MODIFIED blocks for both headers SHALL be retargeted to the post-rename header (`Crate stubs at minimal code depth`) and carry the full combined content (founding runtime stubs + `identus-adapters-entropy` + by-reference admission + `identus-derive` exclusion; derived workspace-dep set including both `identus-adapters-entropy` and `identus-derive`). Because `add-domain-newtype-macro`'s retargeted MODIFIED header does not exist in the current main spec until this change archives, `add-domain-newtype-macro` is archive-blocked-by this change and not standalone-`openspec validate`-able in the interim. This change does not restate the proc-macro / `identus-derive` modifications themselves. No spec deltas are produced for `workspace-dependency-conventions` or `nix-tooling` (the `ring` workspace entry and the new stub fall under their existing rules).

## Impact

- **`openspec/specs/crate-ring-layout/spec.md`**: gains ADDED requirements (adapter-family crates; `identus-adapters-entropy`; composition-root-only dependency; guard derives count from `LAYER_RULES`); RENAMES `### Requirement: Twelve crate stubs at minimal code depth` → `### Requirement: Crate stubs at minimal code depth` with a non-literal body (founding runtime stubs + `identus-adapters-entropy` + by-reference admission of future adapter-family stubs; no fixed total count); and MODIFIES `### Requirement: Workspace dependency map` to a `LAYER_RULES`-derived count (no literal). This change therefore intentionally collides with `add-domain-newtype-macro` on those two headers; see "Capabilities" above for the ordered-archive reconciliation.
- **`crates/conformance/src/lib.rs`**: `LAYER_RULES` gains `identus-adapters-entropy` in `outer-boundary` membership; the two hard-coded `13` count assertions (`every_crate_appears_in_exactly_one_layer`, `manifests_conform_to_layer_rules`) SHALL derive from `LAYER_RULES` membership; the production-must-not-depend-on-outer check SHALL derive its outer/verification set from `LAYER_RULES` (`OuterBoundary` ∪ `Verification`) instead of the hand-maintained `OUTER_CRATES` const (which is removed or reduced to a derived helper).
- **`crates/adapters-entropy/`**: new crate stub — `Cargo.toml` (`identus-crypto.workspace`, `identus-core.workspace`, `ring = { workspace = true, optional = true }` behind a `ring` feature, `default = []`) and `src/lib.rs` (`COMPONENT` + doc-comment).
- **Root `Cargo.toml`**: `[workspace.dependencies]` gains `identus-adapters-entropy = { path = "crates/adapters-entropy" }` and `ring = "0.17"` (entropy is the sole workspace consumer of `ring`; `add-crypto-capability` no longer declares `ring`).
- No production lib crate gains a dependency on an adapter crate (inward policy unchanged); the new crate is a leaf consumed only by binaries/bindings.
