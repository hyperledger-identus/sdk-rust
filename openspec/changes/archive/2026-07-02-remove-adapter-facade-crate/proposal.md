## Why

The `add-adapter-crate-layer` change split `outer-boundary` into per-port-family `identus-adapters-<family>` crates (one per entropy, storage, transport, resolver, openid4vc), each cohesive and dep-isolated, and explicitly rejected the monolithic "one grand `identus-adapters` crate" on cohesion and compile-leakage grounds. It retained the original `identus-adapters` crate only as a non-breaking concession — "the cross-cutting/facade home for adapter concerns that don't belong to a single port family" — and flagged in its own Risks that it "may be repurposed or removed in a future change once the family split is complete." That split is now complete in shape: every concrete adapter family is meant to live in its own `identus-adapters-<family>` crate, and no production crate, composition root (`identus-bindings`), binary, or example depends on `identus-adapters` today. The retained crate is a pure stub (a `COMPONENT` const) whose own `lib.rs` doc-comment already contradicts the spec by claiming it "owns concrete transport, storage, and resolver adapters" — exactly the concerns the family crates now own. The cross-cutting role it was kept for has not materialized and, on inspection, every candidate for it (facade re-export, composition wiring, cross-family shared types, cross-family test fakes) belongs elsewhere (`identus-bindings`, orchestration, `identus-core`, or `identus-conformance`). The crate is therefore dead weight that muddies the `outer-boundary` layer's meaning. This change removes it and restates the layer as *adapter-family leaf crates plus the composition root*.

## What Changes

- **BREAKING (workspace-internal only):** remove the `identus-adapters` crate — delete `crates/adapters/` (`Cargo.toml` + `src/lib.rs`); drop `identus-adapters = { path = "crates/adapters" }` from root `Cargo.toml` `[workspace.dependencies]`; remove the `identus-adapters` `Member` entry from the `outer-boundary` layer of `LAYER_RULES` in `crates/conformance/src/lib.rs`. No production crate, `identus-bindings`, binary, or example declares `identus-adapters` as a dependency today, so this is breaking only in the sense that the crate name ceases to exist.
- Restate the `outer-boundary` layer in `crate-ring-layout`: the layer comprises the `identus-adapters-<family>` leaf crates (one per port family) plus `identus-bindings` (the composition root that wires selected adapter families into runnable artifacts). The "retained `identus-adapters` cross-cutting/facade" clause is removed; the layer's defining sentence makes its dual character (adapter leaves + composition root) legible.
- Drop `identus-adapters` from the founding runtime stub enumeration in the `Crate stubs at minimal code depth` requirement (it is no longer a stub because it no longer exists).
- Retarget the conformance guard's outward-dependency-rejection test assertion that names `identus-adapters` (currently `assert!(check_dep_edge("identus-did", "identus-adapters").is_err());`) to a surviving `outer-boundary` crate (`identus-adapters-entropy` or `identus-bindings`), so the guard continues to prove that a domain crate depending on an outer crate is rejected.
- The conformance guard's count assertions and outer-set derivation already derive from `LAYER_RULES` membership (per `add-adapter-crate-layer`), so removing a `Member` entry requires no literal edit and no new guard logic.

## Capabilities

### Modified Capabilities

- `crate-ring-layout`: the `outer-boundary` layer loses the `identus-adapters` facade crate and is restated as adapter-family leaf crates + `identus-bindings` (composition root); `identus-adapters` is dropped from the founding runtime stub enumeration; the outward-dependency-rejection test target is retargeted.
